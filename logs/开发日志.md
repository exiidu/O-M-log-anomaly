# 开发日志（考题一：智能运维技术向）

记录开发过程中的决策、遇到的问题与解决思路，供复现与评审参考。

## 2026-09-07

### 阶段：需求梳理与方案设计
- 阅读赛题：目标为日志解析、异常检测、漏报/误报分析三项，并交付含代码、说明、开发日志、日程、报告的 GitHub 仓库。
- 调研三类方法（模板 / 统计 / 大模型），最终选定 **Drain 式模板解析 + 窗口统计特征 + Isolation Forest** 作为主方法；规则作为可解释补充与参考基线。
- 重要调整：原计划采用「块级 blockid」粒度。实测发现 `HDFS_2k.log` 2000 行对应约 1994 个唯一块（几乎每块 1 行），块级聚合特征会退化，故与用户确认后改为 **10 分钟时间窗粒度**，验证以 WARN 规则为参考真值。

### 阶段：M1 环境与骨架
- 系统 Python 3.12 无 pandas/sklearn，因此在项目内创建 `.venv` 虚拟环境安装依赖，避免污染全局。

### 阶段：M2 解析（parse_drain.py）
- 实现正则字段化（时间/线程/级别/组件/消息/`blk_` 块ID）与变量归一化模板（数字、IP、路径 → `<*>`）。
- 结果：2000 行全部解析、0 跳过；识别 6 类组件、16 个模板。

### 阶段：M3 特征（feature_build.py）
- 以 10 分钟窗（124 窗）为分析单元，聚合：总条数、模板种类、事件密度 + 各模板频次。
- 注意：特征**不包含 WARN 信号**，以保证孤立森林与规则方法信号源独立，交叉验证更有意义。

### 阶段：M4 检测（detect_if.py / detect_rules.py）
- Isolation Forest（n_estimators=200, contamination=0.2, random_state=42）→ 25 个异常窗。
- WARN 规则基线 → 42 个异常窗。

### 阶段：M5 评估（evaluate.py）
- 合并 IF 与规则结果，得到混淆矩阵 TP/FP/FN/TN 与 P/R/F1。
- 遇到问题 1：CLI 参数 `--if` 与 Python 关键字冲突导致语法错误，改为 `--if_out`。
- 遇到问题 2：`n_warn` 在 merge 中与特征列同名冲突，改为参考只保留 `y_ref`。

### 阶段：M6 报告（report.py）
- 汇总所有中间结果生成一页 Markdown 报告，包含代表异常样本文本（真实 WARN 行 + 高频误报窗口对照）。

### 阶段：M7 交付
- 编写 README（使用说明）、run_all.py（一键复现）、本开发日志、日程.md。

### 阶段：工具增强（桌面交互 + 多格式）
- 增强 `parse_drain.py`：新增通用格式解析 `[时间][级别][来源:行号] 消息`，与 HDFS 格式自动识别切换（同一函数 `parse_line` fallback），支持解析 Windows 组件等非 HDFS 日志。
- 增强 `report_html.py`：参数化 `--input / --output / --title`，并新增 `--with-anomaly` 显式开关 —— 无异常信号的日志默认生成「纯解析统计」报告，异常板块自动降级为说明文字，避免误读 HDFS 的评估文件造成错配。
- 新增 `log_parser_gui.py` + `run_gui.bat`：Tkinter 桌面窗口（零额外依赖），三步操作「选文件 → 解析并生成 HTML 报告 → 在浏览器打开」，内置现代扁平配色、悬停反馈、状态栏与运行日志；封装为可复用工具，解析/报告逻辑与 CLI 共用同一底层代码。
- 交接注意：`parse_drain.py` 输出固定命名为 `parsed.csv`，批量处理多日志时应先各自存独立 CSV，避免互相覆盖。

## 已知局限与后续方向
- 数据为小样本 HDFS_2k，无官方块级标注；验证尺度为与规则信号源的一致性。
- 后续可用带标注的 HDFS_v1（11M 行）做块级精确评估；可加入 SHAP 特征归因增强孤立森林可解释性。
